# 原生桌面与受预算约束的图像处理

采用 Rust 图像核心、egui/eframe 原生桌面和共用核心的命令行入口，以有限的活跃解码任务、逐帧 GIF 与有界预览支持低内存批量处理。该方案便于控制应用资源，不依赖系统 WebView；代价是自行实现原生工具界面，并维护 MozJPEG、libwebp 等编解码依赖的跨平台构建。

处理预算默认 1536 MiB，给界面、驱动与额外分配预留空间；预算是调度估算，不等于操作系统强制上限，必须用进程树的实际内存验证空闲 100 MiB、处理峰值 2048 MiB 的验收目标。各独立工具分别生成自己的处理计划，复用核心管线；纯无损路径保留其格式契约，不能为了压缩率而引入未声明的信息损失。

Windows 的 Glow 驱动在首次编译着色器后可能让编译工作区长期驻留，导致空闲内存超过目标。实测中，`glReleaseShaderCompiler` 和首绘后的 `glFinish` 没有解决驻留问题；同界面切换到 wgpu/D3D12 的内存更高。因此保留上游 eframe/Glow，在主进程创建图形上下文前，由同一可执行文件的短寿命子进程完成相同渲染器的真实绘制，然后正常退出。子进程使用 DWM cloak 隐藏、关闭任务栏入口和激活，不导入图片或保存应用设置；实际绘制、隐藏状态、像素回读和正常退出通过诊断验证，不修改驱动缓存或裁剪工作集。

这用少量启动时间换取较低的主窗口驻留内存，收益依赖驱动缓存，不能承诺所有机器都达到同一数字。初始化最多等待 5 秒，超时后只终止自己创建的子进程，再等待最多 1 秒确认退出；失败仍继续打开主窗口，诊断记录是否确认回收，此时不保证缓存或内存优化生效。macOS/Linux 不启用此 Windows 专用步骤。内存指标与实际平台覆盖见 [验证记录](../VALIDATION.md)。
